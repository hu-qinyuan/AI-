## 1. 项目概述

### 1.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 项目名称 | AI宿造局（暂定，可加副标题"校园闲置与互助智能枢纽"） |
| 产品形态 | 微信小程序（MVP）／Uni-app 跨端可延展为 H5 |
| 目标用户 | 高校"一站式学生社区"住宿学生（首批试点：泓江书院） |
| 核心场景 | 宿舍闲置物品流转、旧物低碳改造、碎片化时间与技能互助 |
| 核心引擎 | AI Agent（视觉识别 + 文本生成 + 意图提取 + 文生图） |
| 交付周期 | MVP 单周期交付，范围见第 8 章 |

### 1.2 产品定位

面向高校"一站式学生社区"的轻量级应用，以 AI Agent 为核心引擎，解决宿舍闲置物品积压、社交互助无门的痛点。定位不是"又一个二手交易平台"，而是**社区内部的物品与时间流转枢纽**：交易半径限定在楼栋／书院内部，履约以"当面交付、顺手带走"为主，弱化价格博弈，强化人情与效率。

### 1.3 核心理念

1. **去交易感**：不做冷冷的价格列表，用 AIGC 给闲置物品赋予情绪价值（故事化文案、毕业纪念、断舍离仪式感），让"转手"变成"传递"。
2. **盘活两类闲置**：一类是**物**（用品、旧物、废料），一类是**时间与技能**（带饭、借工具、拼单、代取快递）。两者共用同一套"发布—匹配—履约"骨架。
3. **AI 只做减法**：AI 的职责是降低发布门槛、提高匹配命中率，不替代用户决策；所有 AI 产出必须可编辑、可一键重生成。

### 1.4 目标与非目标

**MVP 目标**

- 用户从拍照到发布一条闲置，全程操作 ≤ 3 步、≤ 60 秒。
- 互助需求从口语化输入到结构化卡片，字段提取准确率 ≥ 80%（人工抽检 50 条）。
- 单校区／单书院内测，日活 ≥ 50，发布转化率（进入发布页→成功发布）≥ 60%。

**明确不做（本期范围外）**

- 不做在线支付、担保交易、物流配送（全部走线下当面交付）。
- 不做跨校／跨城市流通，不做全站推荐算法（仅做书院／楼栋范围内的规则匹配）。
- 不做商家入驻、广告位、信用分体系。
- 不做独立后端服务器与自建数据库（优先使用微信云开发）。

## 4. 功能详述（开发清单）

### 4.1 模块 1：AI"智"造发布

**功能描述**：用户拍照上传闲置物品，AI 自动识别物品并生成带 Emoji 的风格化文案，同时补齐类别、成色、建议价等标签，用户确认后一键发布到社区广场。

**交互流程**

| 步骤 | 用户动作 | 系统响应 | 边界处理 |
| --- | --- | --- | --- |
| 1 | 进入 Tab 1，点击相机图标 | 唤起拍照 / 相册选择 | 未授权相机时引导开启权限 |
| 2 | 上传 1 张图片（≤ 10MB，支持压缩） | 本地压缩至 1080p 长边后上传云存储，返回 fileID | 多图上传本期仅取首图 |
| 3 | 选择文案风格（3 选 1，默认"极简断舍离"） | 调用工作流 A，返回结构化结果 | 生成失败可重试，最多 2 次 |
| 4 | 查看生成结果，可编辑标题/正文/价格/标签 | 实时保存草稿到本地 | 生成中展示骨架屏，禁止重复提交 |
| 5 | 点击"发布" | 写入 posts 集合，跳转至广场 | 发布前校验必填：图片、标题、类别、取件位置 |

**字段清单（发布表单）**

| 字段 | 类型 | 必填 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `images` | array&lt;string&gt; | 是 | 用户上传 | 云存储 fileID，MVP 仅 1 张 |
| `title` | string | 是 | AI 生成 + 可编辑 | ≤ 20 字 |
| `desc` | string | 是 | AI 生成 + 可编辑 | ≤ 200 字，含 Emoji |
| `category` | enum | 是 | AI 识别 + 可改 | 数码/书籍/衣物/生活/运动/其他 |
| `condition` | enum | 是 | AI 识别 + 可改 | 全新/九成新/七成新/能用就行 |
| `price` | number | 否 | AI 建议 + 可改 | 0 表示免费赠送 |
| `dealMode` | enum | 是 | 用户选择 | 赠送 / 低价转让 / 交换 |
| `location` | string | 是 | 用户选择 | 楼栋 + 房间号（对外仅展示到楼栋） |
| `tags` | array&lt;string&gt; | 否 | AI 生成 | ≤ 5 个关键词 |

**验收标准（AC）**

1. 单条发布从上传到落地，正常网络下 ≤ 60 秒完成，AI 环节 ≤ 10 秒。
2. 三种风格产出的文案肉眼可辨别差异（同一张图分别生成后对比，风格词、语气、Emoji 密度明显不同）。
3. AI 输出必须为合法 JSON，前端解析失败时降级为"仅图片 + 用户手填"，不得阻断发布。
4. 生成文案不得出现价格承诺、品牌贬损、虚假成色描述。

### 4.2 模块 2：旧物"魔法"工坊

**功能描述**：针对卖不出、扔可惜的闲置旧物，提供低碳改造方案与图文教程，附带效果图，形成"旧物 → 新用途"的闭环并沉淀为可分享内容。

**交互流程**

| 步骤 | 用户动作 | 系统响应 |
| --- | --- | --- |
| 1 | 进入 Tab 2，输入物品名（如"空快递纸箱"）或拍照 | 若拍照，先经工作流 A 识别出物品名，再进入改造 |
| 2 | 选择改造场景（宿舍桌面 / 收纳 / 装饰 / 宠物 / 其他） | 传入工作流 C |
| 3 | 点击"求改造" | 返回 3 套方案：名称、难度、耗时、材料清单、分步骤说明、效果图 |
| 4 | 查看方案详情，可收藏、可生成分享图 | 写入 upcycle_records 与 favorites |
| 5 | 完成后可上传成品图，标记"已改造" | 计入碳减排统计 |

**输出字段**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schemes[].name` | string | 方案名，≤ 12 字，需口语化 |
| `schemes[].difficulty` | enum | 简单 / 中等 / 有点挑战 |
| `schemes[].minutes` | number | 预计耗时（分钟） |
| `schemes[].materials` | array&lt;string&gt; | 需要额外准备的材料，尽量为零成本 |
| `schemes[].steps` | array&lt;string&gt; | 4～8 步，每步一句话 |
| `schemes[].effectImage` | string | 效果图 URL |
| `schemes[].greenNote` | string | 一句话说明减碳/减废意义 |

**验收标准（AC）**

1. 3 套方案在思路上不重复（如：收纳类 / 装饰类 / 实用类各一）。
2. 材料清单以"宿舍现有 + 零成本"为优先，禁止出现需网购专业工具的方案。
3. 效果图与方案描述一致，不得出现与物品无关的画面。
4. 全流程（含效果图生成）≤ 30 秒，超时可先返回文字方案、图片异步补全。

---

### 4.3 模块 3：碎片互助广场

**功能描述**：把闲置时间与技能流转起来。用户用一句口语化的话表达需求，AI 自动提取时间、地点、需求内容、酬劳等要素，生成结构化互助卡片，并按楼栋／书院定向推送与撮合。

**示例输入 → 输出**

> 输入："明天谁去二食堂，求带个肉包，重谢"

| 字段 | 提取结果 |
| --- | --- |
| 类型 | 代买/带饭 |
| 时间 | 明天（需结合当前日期归一化为具体日期） |
| 地点 | 二食堂 |
| 需求 | 带一个肉包 |
| 酬劳 | 重谢（非货币酬劳） |
| 紧急度 | 普通 |

**交互流程**

| 步骤 | 用户动作 | 系统响应 |
| --- | --- | --- |
| 1 | 进入 Tab 3，长按录音或输入文字 | 语音走转写，得到原文（≤ 100 字） |
| 2 | 点击"生成互助卡" | 调用工作流 B，返回结构化字段并预填表单 |
| 3 | 确认/微调字段（时间、地点、酬劳、可见范围） | 可见范围默认"本楼栋"，可放宽至"本书院" |
| 4 | 发布 | 写入 mutual_tasks，并向范围内用户推送订阅消息（可选） |
| 5 | 他人"接单" | 状态 待接单 → 已接单 → 已完成 / 已取消，双方可见联系方式 |

**状态机**

```
待接单 --接单--> 已接单 --完成--> 已完成
   |                 |
   +--超时/取消--> 已取消 <--取消------+
```

**验收标准（AC）**

1. 50 条口语样本抽检，时间／地点／需求三项提取准确率 ≥ 80%；缺失字段留空并高亮提示，不得编造。
2. 相对时间（今天/明天/后天/本周五）必须结合服务端时间归一化为 `YYYY-MM-DD`。
3. 同一用户 24 小时内重复发布相似需求，提示"你已发布过类似需求"。
4. 卡片信息流按"可见范围 → 发布时间倒序"排序，已过期（超过约定时间 2 小时）自动折叠。

### 4.4 模块 4：我的"局"子

**功能描述**：个人中心，管理"我的发布 / 我的互助 / 我的改造收藏"，并以碳减排成就卡形成正向反馈。

**功能点**

| 子页面 | 内容 | 数据来源 |
| --- | --- | --- |
| 我的发布 | 我发起的闲置，含状态（在架/已送出/已下架） | posts |
| 我的互助 | 我发起的互助 + 我接的单 | mutual_tasks |
| 改造收藏夹 | 收藏的改造方案，含"已改造"标记 | favorites / upcycle_records |
| 碳减排成就 | 累计流转件数、互助次数、折算减碳 kg、等级徽章 | carbon_stats |

**碳减排折算口径（本期简化）**

| 行为 | 折算系数 | 说明 |
| --- | --- | --- |
| 闲置物品成功流转 1 件 | 2.0 kg CO₂e | 按平均小件物品替代新品估算 |
| 旧物改造完成 1 件 | 1.0 kg CO₂e | 按避免新增购买估算 |
| 互助完成 1 次 | 0.2 kg CO₂e | 象征性计分，不参与排名 |

> 口径需在页面明确标注"估算值，仅用于激励展示"，避免与正式碳核算混淆。

**验收标准（AC）**

1. 各计数与列表数据一致，删除/下架后数量同步更新。
2. 成就等级按累计减碳分档（如 0-10 / 10-30 / 30-60 / 60+ kg），升级时有一次轻提示。
3. 页面空态有引导文案与直达按钮。

## 5. AI 技术实现路径

### 5.1 总体策略

把复杂后端逻辑交给 Agent 平台。推荐使用 **扣子（Coze）** 或海报推荐的 **WorkBuddy**，搭建 3 条工作流（Workflow），以 HTTP 方式暴露为 API，小程序云函数只做转发与鉴权，不自建模型服务。

**三条工作流**

| 工作流 | 职责 | 输入 | 输出 | 依赖能力 |
| --- | --- | --- | --- | --- |
| WF-A 闲置发布 | 识图 + 写文案 + 打标签 | 图片 URL、风格 | JSON 结构化商品信息 | 视觉大模型 + 文本大模型 |
| WF-B 互助提取 | 口语 → 结构化卡片 | 原始文本 | JSON 互助字段 | 文本大模型（NLU/抽取） |
| WF-C 旧物改造 | 生成 3 套 DIY 方案 | 物品名、场景 | JSON 方案 + 效果图 | 文本大模型 + 文生图 |

### 5.2 契约：WF-A 闲置发布

**输入**

```json
{
  "image_url": "https://.../fileID",
  "style": "funny | nostalgia | minimal",
  "user_hint": "可选，如『大一买的，用了半年』",
  "campus_context": "学生宿舍"
}
```

**输出（严格 JSON，不得含解释性文字）**

```json
{
  "title": "毕业前最后的倔强：会发光的台灯",
  "desc": "陪了我三年的小台灯，灯罩有点黄，但光还是暖的🌙 谁拿走继续照亮深夜赶due吧～",
  "category": "生活",
  "condition": "七成新",
  "price_suggestion": 0,
  "deal_mode": "赠送",
  "tags": ["台灯", "宿舍神器", "毕业清仓"],
  "confidence": 0.86,
  "need_manual": false
}
```

**规则**

1. `category` / `condition` 只能取枚举值，越界时回退为 `其他` / `能用就行`。
2. `confidence < 0.6` 时置 `need_manual = true`，前端提示"AI 不太确定，请手动确认"。
3. 文案字数硬约束：title ≤ 20 字，desc ≤ 200 字。
4. 风格差异靠 Prompt 中的语气锚点 + Emoji 密度控制，不允许三种风格共用一套模板。

### 5.3 契约：WF-B 互助提取

**输入**

```json
{ "raw_text": "明天谁去二食堂，求带个肉包，重谢", "now": "2026-11-17T20:00:00+08:00" }
```

**输出**

```json
{
  "type": "代买",
  "title": "求带二食堂肉包",
  "time_text": "明天",
  "time_start": "2026-11-18",
  "location": "二食堂",
  "demand": "带一个肉包",
  "reward": "重谢",
  "urgency": "普通",
  "scope": "本楼栋",
  "missing_fields": []
}
```

**规则**

1. 字段无法确定时填 `null` 并加入 `missing_fields`，**禁止编造**。
2. 相对时间必须基于传入 `now` 归一化；无法解析时保留原文到 `time_text`，`time_start` 置 `null`。
3. `type` 枚举：代买 / 借用 / 拼单 / 代取 / 技能帮忙 / 其他。
4. `scope` 默认"本楼栋"，用户可在前端上调。

### 5.4 契约：WF-C 旧物改造

**输入**

```json
{ "item": "空快递纸箱", "scene": "收纳", "constraints": "零成本、不动剪刀明火" }
```

**输出**

```json
{
  "item": "空快递纸箱",
  "schemes": [
    {
      "name": "桌面三层收纳盒",
      "difficulty": "简单",
      "minutes": 25,
      "materials": ["纸箱 1 个", "胶带", "旧包装纸"],
      "steps": ["拆开纸箱摊平", "按 30×20cm 裁出两块底板", "……"],
      "effect_image": "https://.../effect1.png",
      "green_note": "少买一个收纳盒，约减碳 1.0kg"
    }
  ]
}
```

> 注：`schemes` 数组必须恰好 3 项，上例为简写。

**规则**

1. 恰好 3 套，且场景/思路不重复。
2. `materials` 优先为宿舍现有物，禁止出现电钻、热熔胶枪等专业工具。
3. 安全兜底：若方案涉及明火、刀具、登高，必须在 `steps` 中显式加安全提示。
4. 效果图生成失败时，`effect_image` 置空，前端展示占位图，不阻断流程。

### 5.5 Prompt 与调优要点

| 关注点 | 做法 |
| --- | --- |
| 输出稳定性 | 强制 JSON 模式 + 提供 few-shot 示例 + 输出后做 schema 校验，失败自动重试 1 次 |
| 风格差异 | 每种风格给 3 条参考文案作为语气锚点，并规定 Emoji 密度（搞笑≥4、伤感 1-2、极简 0-1） |
| 幻觉控制 | 成色、价格类字段要求"基于图像可见特征推断"，不可见则留空并标记待确认 |
| 成本控制 | 图片先压缩至长边 1080，识别用轻量模型，文案用文本模型；单次发布 AI 成本目标 ≤ 0.02 元 |
| 可观测 | 每次调用记录 workflow_id、耗时、token、是否降级，便于后续调优 |

### 5.6 降级策略（必须实现）

| 故障 | 降级方案 |
| --- | --- |
| 工作流超时（> 15s） | 返回已识别的品类 + 通用模板文案，提示"AI 开小差了，你可以自己写" |
| JSON 解析失败 | 重试 1 次；仍失败则走纯手填表单 |
| 额度/限流 | 提示"今日 AI 次数已用完"，保留手填发布通道 |
| 图片识别失败 | 直接进入手填，图片照常上传 |

## 6. 技术架构与数据模型

### 6.1 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | 微信小程序原生 / Uni-app | 开发快，可直接用 Vant Weapp 等开源组件库 |
| 后端 | 微信云开发（云函数 + 云数据库 + 云存储） | 免服务器、免自建 API、免鉴权对接 |
| AI | 扣子 / WorkBuddy 工作流（HTTP API） | 可视化编排，改 Prompt 不用发版 |
| 图片 | 云存储 fileID + 临时链接 | 免自建 CDN |
| 消息 | 订阅消息（可选） | 互助卡片定向提醒 |

### 6.2 数据流

```
小程序端（拍照/输入）
   → 云存储（图片 fileID）
   → 云函数 aiPost / aiMutual / aiUpcycle（转发 + 鉴权 + 兜底）
   → 外部 AI Agent 工作流 API
   → 结构化 JSON 回填前端表单
   → 用户确认 → 云数据库（posts / mutual_tasks / upcycle_records）
   → 广场信息流（按书院/楼栋可见范围查询）
```

### 6.3 数据库集合设计（云数据库）

**users**

| 字段 | 类型 | 说明 |

| `_openid` | string | 主键，微信 openid |

**posts**（闲置）

| 字段 | 类型 | 说明 |

| `images` | array | fileID 列表 |
| `title` / `desc` | string | 文案 |
| `category` / `condition` / `dealMode` | string | 枚举 |
| `price` | number | 0 = 赠送 |
| `tags` | array | 关键词 |
| `building` / `college` | string | 可见范围索引字段 |
| `status` | string | `on_shelf` / `granted` / `off_shelf` |
| `aiMeta` | object | 工作流版本、confidence、是否降级 |
| `createdAt` / `updatedAt` | date | 时间戳 |

**mutual_tasks**（互助）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `ownerOpenid` / `takerOpenid` | string | 发起人 / 接单人 |

### 6.4 索引与权限

| 集合 | 索引 | 权限 |
| --- | --- | --- |
| posts | `building + status + createdAt(desc)` | 所有人可读（脱敏 room），仅创建者可写 |
| mutual_tasks | `scope + building + status + createdAt(desc)` | 同上 |
| users | `_openid` | 仅本人可读写 |
| carbon_stats | `ownerOpenid` | 仅本人可读 |

> 隐私红线：对外展示位置只到"楼栋 + 大致时段"，房间号仅在接单成功后对双方可见。

## 7. 云函数与接口契约

| 云函数 | 作用 | 入参 | 出参 |
| --- | --- | --- | --- |
| `aiPost` | 转发 WF-A | `fileID, style, hint` | 商品 JSON / 降级标记 |
| `aiMutual` | 转发 WF-B | `rawText` | 互助字段 JSON + `missing_fields` |
| `aiUpcycle` | 转发 WF-C | `item, scene` | 3 套方案 JSON |
| `createPost` | 落库闲置 | 表单字段 | `postId` |
| `listFeed` | 广场信息流 | `building, college, page, pageSize` | 列表 + 总数 |
| `createMutual` / `takeMutual` / `finishMutual` / `cancelMutual` | 互助状态流转 | `taskId` 等 | 最新状态 |
| `getProfile` | 个人中心聚合 | 无 | 三个列表 + 成就 |
| `recordCarbon` | 碳减排计数 | `type, delta` | 最新累计值 |

**统一约定**

1. 所有云函数返回 `{ code: 0|错误码, data, msg }`，`code != 0` 时前端展示 `msg`。
2. 云函数内做 openid 校验，禁止信任前端传入的 openid。
3. 外部 AI 调用统一 15 秒超时 + 2 次重试上限，超时走降级。
4. 写操作做频率限制（同一用户 10 分钟内发布 ≤ 3 条）。

## 8. 开发计划与里程碑（建议排期）

| 阶段 | 周期 | 交付物 | 完成标志 |
| --- | --- | --- | --- |
| M0 环境与地基 | 0.5 周 | 小程序工程、云开发环境、集合与权限、Tab 骨架 | 四个 Tab 可跳转，云函数可调通 |
| M1 AI 大脑先行 | 1 周 | WF-A / WF-B / WF-C 三条工作流 + 契约自测 | 三份 JSON 在云函数中各调通 10 次 |
| M2 发布闭环 | 1 周 | 上传→AI→编辑→发布→广场 | 端到端 ≤ 60 秒，5 人内测走通 |
| M3 互助闭环 | 1 周 | 口语→卡片→推送→接单→完成 | 50 条样本准确率 ≥ 80% |
| M4 工坊与个人中心 | 1 周 | 3 套方案 + 收藏 + 成就卡 | 方案可用、成就计数准确 |
| M5 打磨与内测 | 1 周 | 空态/异常/降级/埋点、体验优化 | 内测 20 人，无阻断性 bug |

> 关键顺序约束：**M1 必须先于 M2/M3 完成**。AI 工作流是产品差异化的全部来源，若先做界面后接 AI，返工成本最高。

## 9. 风险与应对

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| K1 | AI 生成结果不稳定，JSON 偶发不合法 | 发布流程中断 | 强制 JSON 模式 + schema 校验 + 重试 + 手填兜底（见 5.6） |
| K2 | 视觉识别品类不准，成色判断失真 | 用户不信任，频繁手改 | 低 confidence 时显式提示手动确认；成色仅给建议不做强判 |
| K3 | 互助信息被滥用（骚扰、广告、虚假需求） | 社区氛围恶化、审核风险 | 关键词黑名单 + 发布频率限制 + 一键举报 + 超时自动折叠 |
| K4 | 小程序审核对"AI 生成内容"敏感 | 上架受阻 | 所有 AI 文案可编辑后再发布（用户确认为发布者）、保留举报入口、类目按"校园生活服务"申报 |
| K5 | 用户规模不足，广场冷启动空 | 体验像"空壳" | 内测期由运营导入 30～50 条种子内容；首周做"发布即得成就"激励 |
| K6 | AI 调用成本超预算 | 持续运营压力 | 图片压缩、轻量模型分流、单用户每日额度上限、缓存同类物品识别结果 |
| K7 | 隐私顾虑（房间号、行程） | 用户不敢用 | 位置只到楼栋、联系方式接单后可见、提供"仅本书院可见"开关 |
